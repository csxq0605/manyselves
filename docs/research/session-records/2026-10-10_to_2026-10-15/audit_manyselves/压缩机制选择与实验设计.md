# Manyselves：压缩是否必要、何时触发、应保留什么

日期：2026-10-11。范围：本地源码、历史 usage 账本、已有规范化事实回放、公开一手研究。不调用项目 Provider，不上传客户材料。本轮没有修改生产压缩参数。

## 结论与纠正

压缩有用，但不是每个子智能体的必需步骤。它有三个不同目的：避免窗口溢出、降低后续输入处理量、减少干扰信息。前者可以计算，后两者必须看完整任务的时间和正确率，不能用“摘要更短”代替证明。

前一轮的 0.6 是修复“刚压完又触发”的临时工程参数，不是报告任务最优压缩比例，也不是建议所有 Agent 都压缩。它表示压后目标是触发线的 60%，不保证实际删除 40%，更不表示摘要必须缩成原文的 60%。保留事实和协议完整性可能使目标不可达。

对有明确结束边界的报告子任务，应把“不做 LLM 语义压缩”设为对照基线；完整任务放得下且质量不下降时，可以整个任务不做摘要。长循环优先减少重复证据、过期草稿和已完成操作的冗余；仍需压缩时，再用受保护事实、增量摘要和最近完整交互组合。

## 目前能证明什么

证据：`context_strategy_profile.py` / `context_strategy_profile.json`；完整耗时见 `耗时拆解与压缩收益核查.md`。历史 full-report 运行发生于 2026-09-09，不能用来认证当前维护后的最终质量。

|历史 Agent|正常成功请求数|摘要请求数|最大观测单次输入 tokens|
|---|---:|---:|---:|
|2.2 首次作者|24|0|49,238|
|2.2 模块审核|30|20|83,107|
|2.4 首次作者|19|8|74,234|
|第一章终审|2|0|27,213|
|第三章终审|3|0|20,318|

这说明至少有角色能够走完请求序列而不调用摘要。它不证明该报告质量合格，也不证明其他角色关闭摘要后的峰值一定低于 400K。审核角色可跨多次任务调用复用会话，不能把所有请求都当成一次独立审核。全局累计输入 tokens 也不等于任一 Agent 的上下文长度。

全报告曾有 120 次摘要，占账本 tokens 约 30.07%；摘要请求耗时中位数约 46.37 秒。并行耗时不能直接相加为用户等待时间，也不能据此断言删除摘要就节省某个固定分钟数。摘要后反复补读、重新核验及额外修稿必须一起计算。

五个模块的同一批规范化事实，普通 JSONL 与紧凑事实包相比，字符数减少约 52.2%～61.0%，保留记录及可解码字段。这是表示方式的压缩，非 LLM 摘要；不是原始文档体积或 tokenizer 实测降幅，也不证明原始文件已被完整解析。它说明应先减少格式重复，而非先删具体事实。

## 40K、400K 和模型窗口

本文 K 均指 tokens，不是中文字数。若任务完整轨迹只有 40K，而有效窗口有 400K，窗口容量本身不要求摘要。若任务轨迹本身接近 400K，窗口也只有 400K，则还需给输出、工具返回和下一轮增长留空间。

补充口径：上表的“单次输入”已经包含该次携带的历史，并非本轮新增内容。2.2 作者 24 次输入累计 822,250 tokens，最大一次为 49,238；累计输入中 773,248（94.04%）命中缓存。窗口充足只说明没有容量上的强制压缩需求，不排除压缩减少未来多轮重复输入的价值。净收益还要看缓存、剩余工作及摘要/补读开销，详见 `累计上下文与缓存收益核查.md`。

当前本地配置模型名是 `mimo-v2.5`。小米官方当前标称 1M tokens 上下文、128K 最大输出；这不证明本项目接入路由和历史部署具有相同限额。[官方模型规格](https://mimo.mi.com/models/en-US/mimo-v2.5)

源码 `manyselves/runtime/loops/agent_loop.py` 的 `_context_window_for_request` 在拿不到窗口信息时回退为 128,000。它参与摘要输入及相关重建边界，不能据此声称所有实际请求都被限制在 128K。`working_memory_tokens` 的 36,000 又是独立的估算触发值；因此现有触发不能由官方模型窗口推导出来。

模型能接收的长度也不等于模型在该长度下能稳定提取测点、否定条件、数值单位和引用的长度。后者要用本任务测量，不能把 400K 或 1M 自动视为质量保证。

## 五种机制应分别比较

|机制|适用情况|保留内容与限制|
|---|---|---|
|不做语义压缩|有界作者、短终审、短修改任务|保留完整有效轨迹；允许等价紧凑编码。作为必测基线，不能假定一定最快。|
|等价表示压缩|结构化事实、重复字段/路径|共享表头、枚举、默认值和来源映射；保留单位、位置、异常、缺失及否定。不可省掉决定语义的字段。|
|旧工具结果替换为可恢复引用|已处理的长读取结果、重复结果、旧稿|保留读取参数、版本/已有产物标识、范围、状态和引用；当前决策证据仍直接可见。只有可恢复才可移出，且补读时间计入比较。|
|最近完整交互 + 增量 LLM 摘要|持续修改、长期审核、Chief 长循环|摘要只处理旧摘要及本次要移出的中段；最近交互不必再让摘要模型读一遍。事实不靠摘要作为唯一副本。|
|任务边界重建上下文|新一轮审核、独立模块或新稿修订|以当前稿、当前证据、未解决问题和已接受约束重新构造输入；旧稿历史退出工作上下文。保留修订理由与未闭环项，不把同一未完成工具交互切断。|

工具结果替换并非无损地保留了“模型眼前的信息”：原文还在磁盘，也可能因未被再次检索而遗漏。因此不能盲目清除旧测量结果，然后期待模型主动想起所有已消失的异常。

Anthropic 将 compaction、结构化笔记及工具结果清理作为不同上下文管理方法，并强调保留关键状态、避免过度摘要；这提供设计方向，不提供本任务最优阈值。[官方文章](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

JetBrains/TUM 的工作比较不管理上下文、旧 observation masking、LLM 摘要及混合方案；它表明应加入更简单的对照，并考察摘要对任务轨迹的影响。其编码任务结果不能直接用来证明配电报告的测点召回或引用准确性。[论文](https://arxiv.org/abs/2508.21433)

OpenHands 的公开实现将窗口压力与事件数量启发式区别处理，保留头尾、总结中间，并尊重完整交互边界。它的减半策略是实现选择，不是本项目应照搬的最佳值。[官方源码](https://github.com/OpenHands/software-agent-sdk/blob/main/openhands-sdk/openhands/sdk/context/condenser/llm_summarizing_condenser.py)

## 推荐的语义压缩形状

```text
系统/任务约束
+ 当前任务完整事实包及来源坐标（必要时按明确范围分片）
+ 当前稿与审核状态（按角色选择，不能无差别塞入全部旧稿）
+ 增量摘要：已完成事项、已接受决定、未解决问题、不确定项
+ 最近 K 个完整交互单元
```

下一次摘要输入应为“上一版摘要 + 本次新移出的旧交互”，而非每次扫描全部可见历史。需要追溯的原始内容继续保存在现有 conversation/artifact 中。重要事实及约束应从权威来源重新装配，不能不断从上一版摘要里转述；这样才能减少多次摘要累积的偏差。

这里的 K 不是消息条数。一轮工具调用可能包含 assistant 请求、多个 tool result、后续 assistant 回复；部分协议还有必须随历史保留的字段。应保留完整协议单元，再按实际 tokens 判断。试验候选为最近 2 / 4 / 8 个完整单元，而不是现在直接选定“最后 4 条消息”。

当前实现仍有研究差距：摘要准备接收现有完整历史再筛选，并非严格只总结将要淘汰的中段；全局默认也没有证明适合不同角色。前一轮修复了压后空间不足，并未完成这些策略比较。

## 上限如何得出

区分三项：触发上限 T、压后目标 L、摘要自身长度 S。三者不应由一个固定比例代替。

硬约束：请求总上下文（含工具定义及协议开销）+ 输出预留 + 下一轮增长预留，不超过接入服务有效窗口。服务若把输入/输出分别限额，则分别按其合同计算，不强行套共用窗口公式。

质量约束：通过本任务验证的最大有效输入长度，可能低于服务窗口。触发上限应不超过这个质量边界，同时保留实际输出与工具增长空间。压后应能继续完成一段工作，而不是下一轮再次触发。

没有证据支持现在直接宣布 36K、128K 或窗口的 80% 最优。本项目观测到正常输入峰值约 20K～83K，因此适合先比较不做语义摘要与 64K / 128K 两档；若长循环未结束时确有更大轨迹，再比较 256K。以上是候选实验点，要求接入窗口足够，并统一使用实际/校准 token 计量，不能拿旧 36K 估算值与 Provider 实测值直接排序。

压后目标更合理的约束是：在保留必要内容的前提下，为预期下一阶段的增长留空间。例如预期还增长 20K，则 T 与 L 至少应留出约 20K 的空间；实际增长用轨迹统计，而非永远写死 40% 的删除量。若保留内容本身已经太大，应切分任务或定向装配事实，不应强迫摘要删除事实。

## “最大压缩比例”应如何理解

统一采用删除比例 `1 - 压后长度 / 压前长度`；“压到 10%”等价于“删除 90%”。同时分别记录整段上下文删除比例与旧历史删除比例，避免用旧聊天的高压缩率夸大整体收益。

假设 100K 输入里，系统/任务和必要事实共 30K，最近完整交互 12K，仍需 4K 的摘要/状态，那么本次设计的保留底线为 46K，整段最多减少约 54%。这是这些保留条件下的算术边界，不是信息论极限，也不是报告任务的实测参数。即使把某些旧聊天总结得非常短，也不能突破事实及当前工作所需的底线。

因此不建议设“必须压掉 80%/90%”。重复格式可以高比例压缩；具体测点、数值、单位、位置、否定结论和来源关系应保持可精确恢复且当前任务可访问。摘要长度可从 2K / 4K / 8K 候选比较，但不包括被保护的事实包，也不能为满足长度而默默删除未解决问题。

## 可执行的比较顺序与验收

1. 固定当前修复后的代码、输入、任务和角色定义，先比较三组：不做语义摘要；仅清理可恢复旧工具结果；受保护事实 + 中段增量摘要 + 最近完整交互。所有组使用相同事实包与读取修复，避免把其他改进误归因于压缩。
2. 先覆盖一个有代表性的完整作者任务、一个多轮审核及一个 Chief 长任务，再扩展到整报告。短终审也保留为不应平白增加摘要的对照。
3. 优先测试一个中间候选，例如 128K 触发、最近 4 个完整单元、4K 摘要；它仅用于缩小实验面，不是部署建议。再依失败类型改变一个变量：触发 64K 或 256K、尾部 2 或 8 单元、摘要 2K 或 8K。不要一次把所有参数做笛卡尔积。
4. 首先评估事实和引用：已有回放范围内的 14 条剩余电流、13 条红外、9 条 SPD 记录，以及具体位置/单位/例外/未闭环项。检查该出现的项是否出现、结论是否被来源支持、来源坐标是否可追溯；“存在一个引用”不算引用正确。用独立原始证据作基准，不能让被测摘要自己充当答案。
5. 在一次、三次、五次摘要后检查事实及约束保持率，另测恢复后是否丢失当前稿、未解决审核意见或完整工具交互。对最终稿遗漏、虚构证据、把未知写成合格分别统计，不仅给一个主观总分。
6. 时间比较包含摘要、普通生成、补读、修正和串行尾部的总墙钟时间；同时观察各角色完成时间、请求数、实际输入/输出、缓存命中、重复读取与错误。固定轨迹回放只能测上下文体积和调度，不能替代自由生成的整体质量与耗时。候选策略在相同条件下重复运行，避免单次采样偶然性。

只有质量相当且整体更快，才说明压缩对该角色有净收益。若没有摘要的一组已稳定完成，就保留不做语义压缩；若仅旧工具结果处理更好，就不额外引入 LLM 摘要；若增量摘要更好，再按角色采用。选择可以不同，不强迫整个 harness 一个策略。

当前完成的是机制审查与历史角色画像，不是真实生成对照。本地没有调用外部模型，也没有把客户材料送去公开检索。真实模型对照沿用用户已有保密约束，在明确允许的环境和数据范围内执行。
