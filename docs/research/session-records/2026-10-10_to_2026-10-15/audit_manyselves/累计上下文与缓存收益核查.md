# 累计上下文、缓存与压缩收益核查

日期：2026-10-11。用户已明确将真实模型对照环境留待以后讨论。本轮仅解析本地既有账本并检查源码，无 Provider 调用、客户资料上传、生产参数变更。

## 1. 口径：窗口峰值不等于累计输入

实际组装路径为 `_build_messages` → 当前保留的会话历史 → 工具循环追加调用及结果 → 压缩/上下文重建 → Provider adapter → 请求。发送的不是本轮新增内容。角色跨任务复用会话时，下一次任务也可能带着之前任务的上下文。

每轮输入记为 I(t)：它包括该轮保留的历史，不是增量。窗口容量看每轮 I(t) 及输出等预留；累计输入看所有 I(t) 之和。相邻 I(t) 的差不等于“新信息 tokens”，因为可能发生摘要、删除、任务变化和协议转换。

当前 Anthropic adapter 将未缓存、缓存写入和缓存读取三桶相加为账本 `input_tokens`。缓存命中减少重复处理的开销，但缓存内容仍在模型上下文里；不能把缓存 tokens 从窗口占用中减掉。累计输入也不能直接乘一个统一单价或折算成时间。

## 2. 无摘要作者：82.2 万累计输入中，94.0% 命中缓存

历史 full-report 的 2.2 初始作者共有 24 次成功普通请求，没有摘要：

|请求序号|完整输入 tokens（包含历史）|
|---|---:|
|1|11,790|
|6|25,715|
|12|37,659|
|18|41,344|
|24|49,238|

24 次累计输入为 **822,250**，其中缓存读取 **773,248（94.04%）**、未缓存 **49,002**，缓存写入桶为零。所有这些普通请求的 usage 来源均为 Provider。

49,002 的累计未缓存量接近 49,238 的峰值只是本例观测结果，不能把二者当成一般恒等式。这个例子既证明了重复发送的累计输入很大，也说明累计输入大并不代表每次都从零处理全部历史。不应仅因看到 822K 就立刻对一个峰值 49K 的任务做摘要。

## 3. 同一审核任务内，频繁摘要与低缓存同时出现

为避免混入新任务，本轮将同一 Agent 的连续相同 task_id 划为可观测任务段。task_id 可能复用，因此这不是伪造的精确调用身份；原始 initial 次数也保留在 JSON 中。

2.2 首轮审核任务段 `invoke-current-module-reviewer`：

|阶段|普通请求数|累计普通输入|缓存读取比例|观察到的输入|
|---|---:|---:|---:|---|
|首次摘要之前|9|409,897|85.45%|33,231 → 62,337|
|开始摘要之后|4|315,042|2.93%|73,475 → 83,107|

这个任务段另外做了 4 次摘要：累计摘要输入 **303,589**，摘要输出 **7,934**，摘要请求 active 时间合计 **222.93 秒**。四次后续普通请求之间又不断摘要。

这是值得修复/比较的异常模式，但不是压缩净效果的因果证明。摘要前最后一次请求到摘要后下一次请求之间还有模型输出、工具结果等新增内容；动态系统提示、工具定义变化和服务缓存行为也可能影响命中。不能断言关闭摘要后每次一定命中缓存，更不能直接把 222.93 秒当作关闭摘要后必省的时间。

2.2 审核角色所有任务合计：普通输入 1,780,033；摘要输入 1,470,650。摘要累计 active 时间约 1,000.59 秒，普通请求约 1,088.24 秒。其摘要开销已与正常工作处于同一数量级，值得优先处理；这些累计时间仍不是整报告墙钟时间。

## 4. 摘要之后还有多少工作

连续摘要请求（包括紧邻重试）合并为一个摘要组，避免把失败重试误算为多次成功压缩。

|历史运行|摘要组数|同任务段剩余 ≤2 次普通请求|同 Agent 本次运行剩余 ≤2 次普通请求|
|---|---:|---:|---:|
|full-report|118|45（38.1%）|28（23.7%）|
|revise-report|18|14（77.8%）|12（66.7%）|

两个口径都需要保留：同一任务快结束，不代表这个角色后续不再接任务，摘要可能被后续复用。因此“同任务只剩两轮”不能直接等价为“这次摘要无用”。但连同 Agent 在本次运行里也只剩两轮时，靠减少未来重复输入收回摘要开销的机会更少。

这些剩余次数是事后统计，在线策略不能提前知道实际还剩几次。可以利用明确的终审/提交阶段、任务状态和增长趋势，不应伪装成能精确预测未来轮数的预算算法。窗口不足时，即使只剩一轮也可能必须缩短上下文。

## 5. 更严格的前后配对仍未显示普遍即时下降

排除跨 task_id 边界，只保留同段内摘要成功、前后都有普通成功请求的组：

|运行|有效配对|后续输入低于前次的配对数|后/前输入比中位数|
|---|---:|---:|---:|
|full-report|95|32|1.0142|
|revise-report|13|0|1.0217|

这表示实际观测的下一次普通请求并未普遍变小；并不表示摘要没有删除内容，更不能替代“同一次请求压缩前后”的精确差值。当前历史账本缺少完整的每轮请求正文，无法重建所有被删掉的测点、重复文本和无压缩峰值。原始会话事件也不等同于完整 Provider payload。

## 6. 全局账本口径与校验

full-report 成功普通请求：405 次、输入 19,315,979、缓存读取 10,957,184（56.73%）；摘要请求：120 次、账本输入 8,334,161、缓存读取 89,280（1.07%）。注意这里普通请求包含 initial 与 followup，因此与先前仅 followup 的缓存比例不同。

摘要 120 次中有 118 次成功 Provider usage 和 2 次错误估算 usage。revision 的摘要 20 次中有 17 次成功 Provider usage 和 3 次错误估算；revision 普通失败请求未纳入成功普通请求汇总。不能把全部账本值称为 Provider 精确账单。

新增脚本 `context_growth_audit.py` 将每个任务段的逐轮输入、缓存、消息数、请求字符数、摘要位置及剩余请求数输出到 `context_growth_metrics.json`。校验通过：每个 Agent/任务段的输入等于缓存读取＋缓存写入＋未缓存；分段请求数及输入和与全运行对应分类总数一致。脚本只读 test，结果写 audit 目录；不导入项目 Runtime、不初始化 Provider。

## 7. 对策略的实际影响

压缩收益需要分成两类：容量/质量需要，以及效率收益。窗口或可靠提取能力已不足时，需要减少输入或拆任务；仅为提速时，需要让未来多轮节省的时间，超过摘要、缓存重新建立和额外补读/修稿的时间。

一个只比较原始 tokens 的示例：摘要输入 60K、输出 2K，之后每轮少发 20K，则至少四轮累计减少的输入才超过 62K 摘要总量。这不是成本或耗时盈亏线：若那 20K 原本命中缓存，而摘要不命中，门槛会不同；输出与输入的处理代价也不同。真实对照留待允许的环境，当前不捏造净收益。

据此调整实现优先级：

1. **先保留稳定前缀。** 系统指令、工具定义和必要事实尽量保持稳定顺序与表示。阶段状态发生变化再更新，不为每一轮重写同样的信息。这里是方向，未在本轮改动生产消息构造。
2. **摘要之后要有足够长的继续工作区间。** 前一轮 headroom 修复已减少模拟轨迹中的立即重复压缩；尚未验证它在真实任务中的收益。不能再把“每轮更新摘要”当成默认机制，否则会反复改变历史并支付摘要开销。
3. **摘要输入只包含上次摘要与新淘汰的中段。** 当前 `_compact_working_memory_async` 虽已计算 evicted，仍把 `messages[1:]` 交给摘要方法；后者优先选取近期单元。摘要读取范围与真正将被淘汰的范围没有严格对齐。应将增量中段作为独立候选，而非先提高固定压缩率。
4. **短任务保留不做语义摘要的正式选项。** 即使累计输入很大，只要窗口、质量和缓存表现允许，也可能比单独调用摘要更好。
5. **新任务边界装配当前所需状态。** 新一轮审核不必继承全部旧稿，但要保留当前事实、未解决意见、已接受约束及来源。旧稿归档不等于旧审核要求可以丢弃。

推荐的组织方式仍是“稳定约束/事实 + 当前状态 + 增量摘要（必要时）+ 最近完整交互”。最终阈值必须结合真实增长与缓存表现；本轮没有把 64K/128K 候选改成新默认。

## 8. 顺带核对了一个容易混淆的适配器行为

Anthropic-compatible adapter 中有 `_drop_historical_tool_replay`：在某些兼容分支中，较早的工具调用/返回会被移除。这与 LLM 摘要不同，因此“没做摘要”本身不能普遍证明所有原始历史都发送了。

本轮仅检查当前本地配置的分支布尔值，确认当前 MiMo 路由启用 cache-control 分支，**没有启用上述删除旧工具回放分支**。未输出密钥，也未调用服务。这不回溯证明历史配置与现在完全相同，不把潜在兼容分支问题当成这次报告错误的既定原因。

## 9. 当前结论的边界

这些是旧运行的离线诊断，不是当前代码新生成结果。下一阶段应保留缓存和累计输入两个指标，同时核验摘要是否保住事实及引用。用户已将实际模型环境讨论延后，本轮不再请求相关授权，也不替用户选择外部数据范围。
