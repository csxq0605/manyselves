# Manyselves Agent 实现复核：速度、成本和质量必须共同成立

日期：2026-10-14。源码：cf29d06（PR #6）。本轮重新读取生产调用链、历史指标和官方实现，新增离线请求形状复现；未调用外部模型、未传客户资料、未改变生产配置或代码。这里是设计建议，不是已落地的新运行时。

## 结论

当前没有证据证明 Manyselves 在同等报告质量下比 Codex + skill 更快、更便宜或更可靠。编译提速是真实局部收益，不能回答整份报告生成速度。专用 harness 的合理目标是以少量不可替代的领域处理，提供可部署、可追溯、可恢复、可重复交付；若同环境的简单单 Agent 方案达到这些要求且整体更好，应简化现有编排。

skill 是过程知识的包装，harness 是执行宿主，两者并不冲突。可以在自己的受控运行时保留精简的任务规程与工具，不需要让客户转到 Codex，也不需要发布 skill。部署位置、模型 API、存储和网络策略共同决定数据边界；“自己写了 harness”不自动等于模型在内网。

## 1. 官方方案对照

以下是机制对照，不是性能排名。官方自报的评测对象不同，不能外推成配电报告提速比例。

| 类型 | 官方实现与核实内容 | 可借鉴处 | 不足或代价 |
|---|---|---|---|
| Codex + skills | 技能先公开名称/描述，选中后再加载正文和资源；官方建议减少累积的过度流程指令。[技能文档](https://learn.chatgpt.com/docs/build-skills)、[提示复核](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra) | 少量规程、按需资源、批处理脚本，减少初始化与交接 | 不自动保证资料完整、规则正确或报告合格；也没有本项目速度实测 |
| Claude Code / Agent 上下文 | Anthropic 区分上下文压缩、结构化笔记与独立上下文，明确激进摘要会损失细节。[上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) | 清理旧工具内容，保留任务状态与可恢复原文 | 外置文件可读取不代表模型会回读 |
| Deep Agents | 文件卸载、历史摘要与缓存中间件；当前 graph.py 仍有明确的组件组装。v0.7 删除基础系统提示、缩短工具说明，将 todos 改为可选。[源码](https://github.com/langchain-ai/deepagents/blob/main/libs/deepagents/deepagents/graph.py)、[上下文管理](https://www.langchain.com/blog/context-management-for-deepagents)、[v0.7](https://www.langchain.com/blog/deep-agents-v0-7) | 优先消除冗余，再做有损摘要；每层机制都应通过消融证明价值 | 文中基础输入减少 65% 是其默认提示/工具/中间件，不是报告总 token 降幅 |
| Google ADK | 滑动事件窗口和重叠摘要；所查 summarizer 在送摘要模型前也会截短工具参数/响应。[文档](https://adk.dev/context/compaction/)、[源码](https://github.com/google/adk-python/blob/main/src/google/adk/apps/llm_event_summarizer.py) | 可配置窗口、明确摘要记录边界 | 通用摘要机制仍会丢事实，不能直接复制作为专业依据保全 |
| Anthropic 多 Agent research | 擅长独立方向的广度检索，也明确大量共享上下文和相互依赖不适合这种架构。[官方工程报告](https://www.anthropic.com/engineering/multi-agent-research-system) | 真正独立的取证/分析可并行，返回紧凑证据 | 多 Agent 增加 token、协调与错误机会；报告一致性不是天然独立任务 |
| Pydantic AI durable execution | 将请求/工具执行接到持久执行后端；区分恢复一个运行与单纯保存聊天记录。[官方文档](https://pydantic.dev/docs/ai/capabilities/durable_execution/overview/) | 完成结果复用、故障注入、恢复边界 | 恢复机制不是模型质量机制，也不必为此换框架 |
| LlamaIndex retrieval | BM25、metadata filtering 与稀疏/稠密结果融合。[官方实现示例](https://developers.llamaindex.ai/python/framework/integrations/retrievers/bm25_retriever/) | 规范库可按版本、条款和设备类别检索并展开上下文 | Top-K 不保证完整枚举，也不证明引用支持结论；不建议为少量已知表格先上向量库 |

共同启示：不是选择最复杂的 Agent 框架，而是减少不必要的模型决策和历史负担，把已知的数据操作交给本地确定性工具。

## 3. 本次新增复现：草稿双份进入请求

脚本：request_shape_probe_1014.py；结果：request_shape_metrics_1014.json。使用真实 WriteResultPartTool、bind_task_context、TaskContextRebuilder 和 Anthropic 消息转换方法；虚构正文，没有 Provider 请求。没有构造网络客户端，也未读取本地密钥。

| 已写草稿段数 | 消息 JSON 字符数 | 当前状态字符数 | 第一段/最新段正文标记出现次数 | 系统/消息缓存标记 |
|---|---:|---:|---|---|
| 1 | 11,485 | 8,714 | 2 / 2 | 1 / 0 |
| 2 | 16,561 | 11,179 | 2 / 2 | 1 / 0 |
| 3 | 21,637 | 13,644 | 2 / 2 | 1 / 0 |
| 4 | 26,713 | 16,109 | 2 / 2 | 1 / 0 |

不是整个请求都重复两遍；是已写正文同时存在于当前状态和历史 write_result_part 参数中。字符数不转换成 token 或费用。该复现保持历史低于压缩阈值，不能外推长运行中所有回合都固定双份。

源码位置：
- runtime/task_context.py:56 每次 render 读取当前 task/revision 下全部 md 草稿。
- runtime/loops/context_rebase.py:262–271 将新状态放在保留的 active history 之前，未消除两者的正文重复。
- runtime/providers/anthropic_provider.py:225 只显式给 system 加 cache_control；普通任务消息没有对应标记。

后果：前一轮“保证不遗忘”的修复增加了材料可靠性，却还未完成输入去重；不断变化的整块状态位于历史之前，也不利于复用后面的缓存前缀。仅添加一个末尾缓存开关不足以解决这个布局问题。

Anthropic 缓存的是到断点为止的整个前缀；应把稳定规程/任务事实与变动草稿分块，在稳定前缀末尾设断点，并读取 cache creation/read 实测。[缓存文档](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

## 4. 慢在哪里：已有数据能回答多少

重新读取历史 latency_compaction_metrics.json，而非把旧结果当成当前 Claude：

- 2026-09 MiMo full-report 记录：525 个请求，其中 355 个 tool_followup、120 个摘要、50 个 initial。
- Provider 观测跨度 7,082.60 秒（118.0 分钟），至少一个请求活跃的时间并集 6,479.60 秒（108.0 分钟）。
- 仅摘要请求活跃的时段并集 596.42 秒（9.94 分钟）。这不是“取消摘要就能节省”的因果估计，摘要也可能延迟后续关键步骤。
- 该记录工具耗时累计 110.80 秒、请求排队累计 85.16 秒；两者是累计量，不能与并行并集直接相加，也不能用缺乏 Provider 活跃的间隙证明都是 Python 开销。
- 历史证据支持优先调查模型往返/生成/摘要，而不支持把全部慢归结于工作流执行器。新版的关键路径分解仍未完成。

一个不涉及生产提速承诺的数量级示例：若每轮新增 d tokens，每轮重发此前全部历史，n 轮累计新增历史输入约为 d*n*(n+1)/2。单次窗口能够容纳只解决能否发送，并不消除累计处理与收费。

## 5. 压缩：有用，但不能同时承诺省 token、提速和无损

旧合成受控轨迹（当前任务投影架构之前，每组仅一次；均无缓存命中）：

| 策略 | 累计 input tokens | output tokens | 含摘要的请求时间累计 | 延迟细节答对 |
|---|---:|---:|---:|---:|
| 不摘要 | 616,894 | 1,836 | 22.281 s | 3/3 |
| 36K 触发 | 421,660 | 3,691 | 28.968 s | 0/3，明确不可用 |
| 12K 触发 | 198,470 | 9,642 | 48.473 s | 0/3，明确不可用 |

这组实验直接显示：输入降了，但摘要输出和耗时增加，细节遗失。它不证明所有压缩都会变慢，也不能用来定当前最佳阈值。

候选策略顺序：
1. 不经 LLM 的去重、过时版本移除、成功写入参数回收，原文可恢复。
2. 稳定事实/规则与变动状态分块，先测真实缓存。
3. 短而有明确输出边界的子任务对照“不做语义摘要”；只保留任务当前状态和协议完整的近期交换。
4. 长任务再增量摘要历史过程；数值、单位、对象、工况、来源、规则条件与未决问题保持准确。
5. 触发阈值同时考虑实际窗口余量、未来剩余请求、摘要耗时、输入/输出价格及遗忘损失。36K/0.6 目前只是配置，不是最优结论，也不是全部请求 36K 上限。
6. 不能给出通用“最大压缩比例”：大量重复日志可大幅减少，密集事实表则很难语义压缩。先确定保真字段与缺陷保留率，再比较各比例。

节省是否成立，比较未来重复输入节省与本次摘要输入+输出+重读+纠错成本；时间另算，不能以 token 下降代替提速。

## 6. 召回与“开始编”应分层修复

当前有本地索引、来源 ID 读取、范围枚举及关键词搜索。project_evidence.py:141 按空格拆词，:164 计字符串出现次数，尚不是该路径上的 BM25/向量融合。

错误链需分别计分：
1. 原文没有被正确解析进证据；
2. 已解析，但选取范围、检索或截断没把它传给模型；
3. 已传入，但模型忽略或混淆对象/条件；
4. 值抄对，却用错规则/推理；
5. 断言没有足够支持，提交/审查仍接受。

“文件可访问”只能证明工具权限；“模型看到材料”也不证明正确使用。曾出现正确写出 16.58 及来源、却按虚构 >10 规则判成正常，这是第 4 类，不是检索能单独解决的。

建议按任务准备最小但充分的资料：已知客户表格按对象和工况完整枚举；已知引用 ID 直接展开原文；规范库再做条款级关键词/语义召回并补版本、适用条件和例外。没有查到、资料不可用、资料明确没有应是不同结论。明确缺失时输出待核实，而非让摘要或模型知识填成现场事实。

无需为了名义 RAG 把客户数据送去新的外部服务；是否引入本地索引依赖具体召回失败及测量。

## 7. 编排建议：保留无状态 Kernel，减少串行认知阶段

当前 tail 仍固定 Cross → Chief → Final；前面还有五组作者/局审。串行阶段、阶段内部工具往返和返工都可能成为关键路径。五模块并行只能减少独立部分，无法消除这些后续依赖。

候选形态：
本地解析/来源定位 → 按对象/条件的有限并行分析写作 → 一次来源充分的合并审查 → 定向修复 → 确定性装配交付。

这是待实验方案，不是直接删除所有审核。规则明确且适用性已确认的数值/单位/计数可由代码计算；审查模型重点处理适用条件、冲突、遗漏及表达超出证据范围。Chief 若只是搬运既有内容，应使用确定性装配；需要跨模块的新分析才值得单独调用模型。Final 是否合并到一次审查，要按遗漏检出与新增返工评估。

不在此阶段加更多常驻审计 Agent，不更换编排框架，不用更小预算掩盖多余工作。

## 8. 如何证明比简单方案值得

分开做两个比较，避免把模型能力差异误归因于 harness：
- 架构比较：同模型、同资料、同工具/输出要求，对比当前流程、精简编排、单 Agent+本地规程工具。
- 产品比较：实际 Codex+规程基线对比实际部署模型；允许模型不同，但结论仅限整套方案，不把差异都算成架构收益。

三者均需同等来源访问范围和交付要求。合成样例至少包括尾部异常、相同数值不同工况、未解析页、缺测、规则例外、来源无关但 ID 有效、压缩后细节、跨模块修复交换矛盾和中断恢复。先固定答案，再匿名核对结论；LLM judge 只能辅助，不能让同一模型自证准确。

计量：端到端时间与 P50/P95（样本不足不报 P95）、首个可审阅结果、模型/摘要/工具/排队/持久化、所有输入输出与缓存桶、真正支持结论的引用、错误/遗漏、修复新增错误和恢复重复调用。各审查层做消融；只保留其质量收益足以抵偿成本/时间的层。

专用 harness 必须提供至少一个实际可验收的优势：受控部署、结构化来源追溯、批量一致交付、已完成结果复用、跨运行增量修订或总体人工复核时间下降。它们不是“用了多 Agent”就成立，也不是别的产品绝对做不到。

下一实施优先级：请求中已持久草稿去重 → 稳定前缀缓存与变动状态分离 → 模型往返/串行阶段消融 → 规则来源补全与召回对照 → 按角色决定是否摘要。先验证前两项再调更激进的压缩比例。
