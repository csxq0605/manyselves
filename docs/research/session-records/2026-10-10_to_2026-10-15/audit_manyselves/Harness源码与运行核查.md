## 2. 为什么“文件能打开，模型却读不到”

应区分五件事：文件存在、解析器成功提取、检索返回、内容进入当次模型上下文、最终结论正确利用。前一项成功不保证后一项成功。

### 2.1 用关键词 Top-K 搜索承担全量数据覆盖，已经与漏写现象对应

当前 `runtime/research_tools.py:46` 的 `search_project_evidence` 强制将 limit 限制到最多 12。即使模型请求 20，仍只返回 12。返回值有 requested/applied limit，但没有全部匹配数、分页游标或按模块全量枚举接口。

`runtime/research/project_evidence.py:111` 按空格拆词，以字符串出现次数计分；同分按 E 编号升序排列。它没有同义词归一化，也没有按字段/模块筛选后保证全量覆盖。长概述与重复的跨模块记录能占据检索名额。

实际案例 A：SPD 漏写。

- 原始证据已存在：`E-0133` 科研楼 1#，`E-0142` 科研楼 2#，内容都是“电涌保护装置=NG”，对应总配表 R9:S9、R10:S10。
- 9 月 9 日作者会话实际搜索“电涌保护器 SPD 避雷器 过电压”；模块 2.3 evidence-memory 也保留该查询。
- 当前搜索函数对同一冻结证据重放，只返回 E-0293、E-0288、E-0246，都是汇总性质材料，不含上述两处 NG。
- 改用“电涌保护装置”，便返回 9 个设备记录及 1 个概述，包含 E-0133、E-0142。
- 模块 2.3 的历史 evidence-memory 没有 E-0133、E-0142；报告最终也漏写科研楼这两处。

这是非常具体的检索措辞缺口，不是 Excel 中不存在数据。仍不能把每一次模型内部决策完全还原，但“原始事实存在 → 实际查询没有召回 → 报告遗漏”已有对应证据。

实际案例 B：剩余电流只列 9 条。

- 源表有 14 条实测数据。
- 2.4 历史查询“剩余电流 实测 占比 变压器 低压侧”，返回 12 条，其中 3 条是其他概述/Skill，剩余 9 条为 E-0028 至 E-0055 的前 9 个测点。
- 当前搜索实现能原样复现这一结果。报告 2.4.3.1 正好列这 9 条，最大值为 2.1 A，并将结论泛化。
- 后面的科研楼和老配电房记录未进入这个结果集，包括另一章节已经指出的 11.3 A 异常。

实际案例 C：红外数据末尾遗漏。

- E-0230～E-0233 已在规范化证据中，代表末尾两条测点的跨模块记录。
- 2.2 evidence-memory 不含这四个 ID；该模块温度查询多次被 Skill、重复记录和其他概述占位。
- 最终报告列 11 条而非源表的 13 条。该关联支持检索覆盖不足，但不证明所有遗漏都只由 Top-K 导致。

### 2.2 14 份角色 Skill 被编成了客户事实

该 Run 的 E-0317～E-0330 对应 `Inputs/report-template-role-skills/*/SKILL.md`。它们的 subject 是 `SKILL.md`，module_id 为 null，fact 是整段方法说明。

这些内容实际出现在客户证据搜索前列，例如 E-0318 占用剩余电流/红外检索名额，E-0323 占用温度检索名额。工具宣称返回 E-* 客户事实，但这批 E-* 实际是写作指令。

当前 `preparation_tools.py:323` 将通用 text/document_paragraph/pdf_page 的正文直接构造为 EvidenceItem。此次输入角色目录由此进入事实库。需要在输入分类和证据类型上区分客户观察、已有评估、方法规则、标准原文、模板；不能依赖模型阅读内容后自行纠正类别。

### 2.3 “已读取”与“仍然可见”不是同一状态

`runtime/tools/artifact_tools.py:38` 和 `:88` 用 `_opened_pages` 去重。相同 ref/offset/limit 再读时返回 `already_read`，content 为空，并要求依赖工作记忆。

`runtime/loops/agent_loop.py:870`、`:3834` 则会移除较旧的完整消息单元，用摘要和近期消息替代。读取工具的集合并未依据当前上下文可见性同步失效。

函数级离线探针已证明：首次读取返回事实，第二次相同读取返回空。结合压缩代码，这是一个确定存在的设计冲突：某页被压缩移除后，模型可能需要重新读取，却被工具认定为无需读取。**本次未证明它直接导致了上述某一条报告错误**，因此将它列为当前代码风险，不当作已还原的历史根因。

另一个冲突：OpenToolResult 默认返回 8,000 字符，而 AgentDefaults 的 `max_tool_result_chars` 默认 6,000。`AgentLoop._format_tool_result` 对它没有专门豁免。离线调用当前函数，8,000 字符页被再次包装成截断预览，只有 4,976 字符，增加了间接引用和读取轮次。具体有效值还可由运行配置覆盖；这里证实的是默认组合问题。

### 2.4 有引用不等于引用支持结论

`module_review_preparation.py:127` 默认从作者已提交 claim 的 source_ids 中选取审查证据。这能核对已写论断，却天然缺少“应该写但作者没写”的事实。审查 Agent 仍可额外检索，因此不能说审查完全无法发现漏项；但遗漏发现没有独立、完整的输入基线。

同文件 `:69` 的确定性检查核对 canonical Markdown；`report_validation.py:32` 检查章节结构和 Markdown。这些检查有价值，但 passed 不代表全量测点一致、所有 NG 覆盖、算术正确、标准适用或引用蕴含成立。系统另有结构化提交和模型审查，不能把这两个函数误称为系统的全部检查；问题是现有通过结果没有阻止已发现的具体漏项。

### 3.1 最明显的开销是上下文维护，不是请求排队

全文的压缩占账本 token 约 30.1%，占累计 Provider 活跃时间约 28.8%。当前 `_request_model_handoff_summary` 通过同一 Provider 再发请求来生成摘要，虽然已关闭摘要推理模式，仍要反复处理旧上下文。

因此“缩小工作记忆/每页内容来节省 token”并不保证总成本下降。它可能增加检索、分页、摘要、恢复和纠错请求；每次又重发当前上下文。现有源码已修复过摘要空输出等历史问题，本结论并不把那些旧故障当成仍未修复。

### 3.2 并行有效，但消不掉串行依赖和慢分支

`distribution-module-cohort.yaml:34` 确实并行执行五个模块；每个模块内部仍有 author → review → revision → recheck。随后 `distribution-reporting-tail.yaml:16` 顺序执行 cross → chief → final → delivery。后段要等待前段结果，每一轮修订又有新的模型调用。

全文累计模型活跃时间远大于首末跨度，说明不能称其为“假并行”。但复制五条复杂循环，不会自动得到五倍加速，也不减少 token 总量。当前修订只明确请求改 2.3.1，但 target_modules 是全部五个模块，实际发生了五个 cross-owner、多个模块改写/复审及总编终审；不能据此推断所有局部修订都必然重跑全量，但这个具体请求确实扩大了后续处理范围。

### 3.3 成本参数目前不是硬预算

`models/reporting.py:415` 有 cost_control_mode、max_provider_attempts、max_total_tokens；`templates/agents/main_agent.md:36` 及当前状态文档明确说明是 observe/display，强制停止未接线。全源搜索对应 max_* 字段，未找到在每次 Provider 派发前执行总量限制的生产代码。

全文请求配置的是 80 次、800,000 token，实际账本为 525 次、28.34M。该请求本身为 observe，因此这是当前契约的可观察结果，不应误说成一个已经承诺硬限额却偶发失效的 bug。用户如果以为这些字段能限制费用，会产生明显认知落差。

预算应在统一请求派发处统计作者、审查、压缩和重试，区分实际 usage 与估算，并处理并发在途额度；强制停止也应保留已完成结果、明确尚未核验部分。仅减少检索权限会把成本压力转化成证据盲区。

## 4. 中断：已有恢复不等于降低失败概率

当前修订 Run 有 9 条 APITimeoutError。异常文字同时涵盖网络超时、连接中断、请求取消，因此不能仅凭它们断定 Provider 服务故障，更不能全部归责于 Harness。日志还证实过：open_tool_result 引用签名错误，以及把模块 JSON 路径传给只接受 E-* ID 的 open_project_source。

恢复机制能重试和延续任务，但数百次调用、很长的 opaque 引用、长上下文、多轮提交，都会增加遇到中断或协议错误的机会。异常后继续发起同样昂贵的过程，也不自动解决诱因。

`provider_agent_session.py:53` 重启恢复返回 messages=() 和 bounded handoff_summary；已完成结果另有持久化复用。它不是完整原上下文原样恢复，恢复后可能需要重新取证。应区分“任务状态可恢复”和“模型工作上下文等价恢复”。

还有待测的本地因素：两个 Run 的 runtime-state.json 约 61.5 MB、66.2 MB。`workflow_host.py:475` 每次嵌套状态转换 checkpoint；并行路径深拷贝分支/父状态；`state_store.py:44` 同步整份 JSON 写入且此实现未使用临时文件替换。这可能阻塞事件循环，也存在写入中进程退出留下不完整文件的窗口。**未进行 profile 或故障注入，不能声称它是此次耗时/中断主因，或给出节省比例。**

## 5. 哪些属于幻觉，哪些属于 Harness 问题

|现象|较准确的归类|应处理的位置|
|SPD/红外记录在库中却未召回|检索覆盖与材料分类缺陷|数据准备、枚举/检索工具|
|只看 9 条后声称全部正常|证据不完整叠加模型过度概括|完整性信息、输出论断边界、审查|
|2.3% 被写为超过 3%|数值比较/推理错误|确定性计算和正文一致性验证|
|已有资料缺口被写成确定故障|无依据推断；可称事实性幻觉|事实/假设类型、缺口表达、审查|
|引用 ID 存在但不支持对象/结论|引用错配或语义归因错误|对象绑定、论断与来源核验|
|方法库本身阈值/适用条件错误|上游知识质量问题|专业知识维护和适用范围|
|重新读取被返回空内容|工具状态与上下文状态冲突|Runtime 读取和压缩策略|

因此，不宜用“换更聪明模型”或“提示词强调认真读”作为主要修复方案；也不能宣称所有问题都由 Harness 决定。需要让模型有完整、紧凑且适用的事实输入，再评价它剩余的分析错误。

## 6. 保留私有 Harness 的改造优先级（建议，尚未实施）

### P0：让有限的表格数据得到完整处理

1. 原始观察、原报告结论、标准/知识、Skill/模板分开建模；方法资料不再进入客户 E-* 检索。
2. 使用现有 module/submodule 归属，确定性构造完整、紧凑的事实包，包含对象、字段、值、单位、源坐标、异常和缺失。14 条剩余电流、13 条测温应直接完整交付；自由关键词搜索用于补充查询。
3. 给每个应核查事实一个处理去向：已用于结论、已说明不适用、证据矛盾或待确认。这里要求事实得到处理，并非每个重复 E ID 都要出现在正文。
4. 审查使用独立的原始事实清单，不只看作者选择的引用。优先检验全部 NG、行数/设备数、汇总与阈值、跨章节相同对象。

可先以现有三份 Excel 和本次已确认问题为回归样本。算术和行数用程序做；复杂标准适用性、风险解释仍由模型及专业人员负责。不要将有问题的知识库原样固化为确定性规则。

### P1：减少无效轮次，而不是继续压缩单次读取权限

1. 已读缓存保留原内容或可直接重新交付的页，区分缓存复用与拒绝重读；权限验证可以保持在服务端。
2. 分页长度与模型可见输出长度采用同一口径，避免“分页结果再次分页”；使用短的服务端引用句柄，减少模型复制长签名字符串的错误机会。
3. 以结构化事实/论断/未决项作为持久状态，任务切换时按需要重建紧凑输入；摘要用于叙事进度，不作为唯一证据记忆。先测量压缩频率，再决定调整阈值。
4. 让作者提交事实选择与分析，程序组装表格/引用/固定结构；修订按明确受影响的小节提交差量，避免重复整篇结构化输出。
5. 在已有统一派发边界实现可解释的预算策略，同时保留安全交接，不把预算失败伪装成合格报告。

### P2：简化审查链与恢复单元

保留 Kernel/Runtime/Capability 分层，不必推倒重建。写作可按独立专题并行；跨章节先用共享对象/事实表解决可确定的冲突；模型复核集中于争议论断和风险解释，限制在明确问题集合内迭代。仅当争议解决或事实覆盖有新增时继续，不靠更多重复阅读来证明质量。

持久化采用较小任务产物与轻量状态引用，测量 JSON 序列化/写入的 p50/p95 后再改存储策略；恢复时重建事实包和未完成任务，而不是寄希望于模型记住整个历史。上述是设计建议，不是已做的代码修改；新增预算/验证机制还需按项目约定确定具体方案后实施。

## 7. 怎样判断改造是否有效

在保密环境内，用相同原始输入、固定代码版本、相同模型/配置做基线和改造后对比，至少重复若干次再判断稳定性。无需把材料交给外部写作工具。

同时测量：完整事实覆盖、严重异常漏报、无依据事实、数值/跨章节冲突、来源支持度；端到端时长和各阶段关键路径；Provider/估算/缓存 token；压缩/修订/重试请求；自动恢复是否需要人工介入。能出 Word 和审查 passed 都不能单独作为验收。

建议先做“完整事实包 + 独立遗漏检查”的小切片实验，再做上下文/分页优化；这样能区分质量改善来自读全、模型变化还是更多计算。当前证据支持这些改造方向，但没有支持“保证快若干倍”或“完全消灭幻觉”的实测结果。
